# Player selection

`getLocalPlayer` selects the entity assigned to a client view through `world.metadata.localPlayerId`. With no assignment it retains the existing single-player first-player behavior. With an assignment, a missing entity produces no player; controls must never take over another actor during reconnects or transitions. This metadata is view-local and is not saved in world snapshots.

`useHero` and the Systems render fallback honor this assignment. `selectViewable` scopes player and popup cameras to that assignment. Building cameras use the selected actor's structure membership, independently of another player's roof toggle. Open dialogs carry an owner. Popup input, camera selection and generated dialog particles use that owner, so other actors cannot operate or see the dialog. Hosted NPC dialogs create independent reader views linked to shared source data. Hosted players keep personal inventory/inspection entity IDs and interaction state on `PLAYER`. The normal interface factory creates these entities for both modes; single-player still uses its existing identifiers. Trigger, action and popup systems resolve the acting player’s interface. Per-player prompt roots use the existing sequence and sprite rendering, with owner-tagged particles and independent hit areas. Interface IDs, selections and prompt roots survive snapshots; respawns reuse and rebind them to the replacement actor.

`getClosestPlayer` chooses the nearest living non-ghost player satisfying the requested components, using the current map's wrapping distance. Equal-distance ties retain entity order. AI behavior patterns use this selector instead of the global `hero` identifier. Scripted quests and boss room sequences still need a separate multiplayer audit; changing target selection alone does not make quest rewards cooperative.
